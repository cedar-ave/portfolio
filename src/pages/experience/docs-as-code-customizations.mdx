# Docs-as-code: Customizations

**I took DocFX, Microsoft's open-source generator built for API reference, and customized it into a customer help site that fit how the company's customers actually read docs.** DocFX's default template gave every site the same generic page: a table of contents, a one-item breadcrumb, *Improve this Doc* links meant for open-source contributors, and a *Generated by DocFX* footer. I kept DocFX's engine and changed what readers and writers touch. I added a version switcher that keeps readers on the same page when they change releases, a feedback form on every article that sends complaints to the docs team, banners that tell readers which product edition a page covers, search that finds file names like `install.config`, and a single-sourcing system of reusable Markdown partials, a terms dictionary, and styled notices that made a product rename a one-line change. Each change had to fix a real reader problem or reduce maintenance. I overrode as few of DocFX's files as I could, made each feature a setting instead of per-site code, and prototyped several ideas that I decided not to ship.

The company's details are left out. Code samples on this page are simplified from my original work, and product names, URLs, and services are replaced with placeholders.

:::tip[At a glance]

- **Built on DocFX's default template, not a rewrite.** I overrode only the template files I needed, shipped them as one theme package, and checked each DocFX release for upstream changes to files I had overridden.
- **Versions that keep your place:** switching releases takes readers to the same page in the other release instead of the home page.
- **Single sourcing:** reusable Markdown partials, a terms dictionary, styled edition notices, and front matter banners, so shared content is written once.
- **A feedback loop DocFX doesn't have:** a *Was this helpful?* form on every article, with responses sent to a sheet and alerts sent to the team's chat channel, plus a report of pages with zero views.
- **Feature switches instead of forks:** more than 20 settings in `docfx.json` that turn features on or off per site, per folder, or per page.
- **Search for technical readers:** file names with periods are searchable, and reusable fragments never appear in results.
- **Better PDFs from the same source:** Markdown cover pages, a fix for a DocFX table of contents bug, web-only and PDF-only content, and a user-only guide made for one customer.

:::

## The starting point: DocFX's default template

DocFX builds a site by applying a template: a master layout, a set of *partials* (reusable pieces of the page such as the head, navbar, breadcrumb, sidebar, and footer), styles, scripts, and a `token.json` file of interface text. The default template is designed for a generic open-source project. The company needed a help site for a suite of healthcare data applications, read by customers on several product versions and two product editions.

This table compares the default DocFX v2 template the site was built on with what I shipped.

| Area | DocFX default template | What I built | Why it mattered |
| --- | --- | --- | --- |
| Breadcrumb bar | One item: the table of contents title | Version switcher, a home icon each site can point anywhere, the breadcrumb, and search | Readers always knew which release and guide they were in |
| Versions | No version support | A dropdown that opens the same page in another release | Customers on older releases found their docs without starting over |
| Reader feedback | None | *Was this helpful?* with reasons and a suggestion box, sent to a sheet and a chat alert | The team heard about bad pages from readers, not from support escalations |
| Right sidebar | *Improve this Doc* and *View Source* links for contributors | *Request a feature*, *Ask the community*, *What's new*, and *Download PDFs*, each switchable per site | Customers aren't repo contributors; they needed ways to get help |
| Footer | *Generated by DocFX* | Legal links from one setting, plus *Edit this page* and *Contributor reference* | Legal text stayed consistent, and employees could fix a page in two clicks |
| Callouts | Glyphicon icons and default labels | Font Awesome icons and colors from the company's design system, in web and PDF | Notes and warnings matched the products customers used every day |
| Search | Splits search terms on periods | Keeps periods, and leaves reusable fragments out of the index | `install.config` returned the right page |
| Feature settings | `_disable*` flags | `_enable*` flags, plus new settings for links, banners, and versions | Non-writers configured sites without reading template code |
| Left navigation | A plain list | Headings, dividers, and *Deprecated* stamps set in `toc.yml` | Long guides were easier to scan, and old features were clearly marked |
| PDFs | Default cover, table of contents, and styles | Markdown covers from shared snippets, a table of contents bug fix, a dated footer | Offline customers got guides that looked finished and showed their date |

## How I decided what to customize

It's easy to customize a static site generator until nothing can be upgraded. I used five rules to decide what was worth changing.

1. **Start from evidence.** Every customization answered a reader problem I could point to, from feedback, analytics, support questions, or a customer request, or it removed maintenance work the team was already doing.
2. **Override the smallest file possible.** DocFX lets a template replace any file in the default template, file by file. I copied only the partials I needed to change, kept a list of them, and checked each new DocFX release for changes to those files so the site could still take upgrades.
3. **Make it a setting, not code.** Each feature reads a value from `docfx.json` or front matter, so a new site turns a feature on with one line instead of copying template code.
4. **Choose the simplest mechanism.** For single-sourced text, I prototyped a Mustache.js version, then shipped a short script instead, so no site took on a new dependency.
5. **Prototype, then decide.** I built several ideas, documented them, and held them back until readers needed them.

| Idea I prototyped | What I decided | Why |
| --- | --- | --- |
| A site-wide banner for prerelease docs | Built it and left it off by default, one setting away | Useful for a preview site, but noise on production |
| *Recommended content* links at the bottom of each page | Built and documented it, didn't ship it | Hand-picked links for every page would need constant upkeep |
| Freeform page tags | Documented the approach, didn't ship it | The applies-to banner met the reader need tags were meant for |
| Mustache.js templates for single sourcing | Replaced with a short script | Same result, one less dependency on every site |
| Copying stylesheets into every folder for nested sites | Rejected for a configurable path | Folder depth varied, so copying would be fragile and slow |

## The page, piece by piece

<PageAnatomy />

1. **Version switcher that keeps your place.** Choosing another release opens the same page in that release. See [Navigation that respects versions](#navigation-that-respects-versions).
2. **Home icon and breadcrumb.** The default breadcrumb showed only the table of contents title. Mine adds a home icon, and each site sets where it points with `_homePath`, so a product section's home is its own landing page, not the root of the domain.
3. **Search for technical terms.** See [Search that works for technical readers](#search-that-works-for-technical-readers).
4. **Navigation headings, dividers, and stamps.** I changed the table of contents partials to pass a `class` from `toc.yml` into the HTML, so writers can add section headings, divider lines, and a *Deprecated* stamp without touching code.
5. **Status banner.** A `statusMessage` line in a page's front matter shows a highlighted notice at the top, such as *coming soon* for a feature that isn't released.
6. **Applies-to banner.** Setting the product editions in front matter shows which editions a page covers.
7. **Single-sourced terms and notices.** Product names and edition notices come from JSON files. See [Single sourcing](#single-sourcing).
8. **Image lightbox and copy button.** Screenshots open full size, with the image's title or alt text as a caption, and every code block has a copy button.
9. **Feedback form.** See [Closing the loop with readers](#closing-the-loop-with-readers).
10. **Help and resources links.** The default sidebar's contributor links became links to request a feature, ask the customer community, read what's new, and download PDFs. Each link turns on with a setting and takes its URL from `docfx.json`.
11. **Footer.** Legal and copyright links come from one setting. *Edit this page* opens the source file in the repo, next to a link to the contributor guide. See [Docs-as-code: Scaling contributions](/experience/docs-as-code-contributions).

## Single sourcing

A help site for several products, two editions, and several releases repeats itself constantly: the same warning in five install guides, the same product name on hundreds of pages, the same support links on every site. Copying that text meant that a rename or a new support URL became a search-and-replace across repos, and some copies were always missed. I built four ways to write it once.

<SingleSourceFlow />

### Reusable Markdown partials

DocFX can include one Markdown file in another, but it treats every Markdown file as a page. Each shared fragment was built as its own HTML page, which showed up in search results as half a page with no context, with its own feedback form and sidebar. I made fragments a convention: shared content lives in `partials/` folders inside a guide or in a site-wide `includes/` folder, and pages pull it in with an include.

```plaintext
articles/
  includes/                 site-wide snippets
    version.md
    release-date.md
    support.md
    legal.md
  admin-guide/
    partials/               snippets shared inside this guide
      permission-messages.md
    manage-permissions.md   [!include[](partials/permission-messages.md)]
    bulk-upload.md          [!include[](partials/permission-messages.md)]
```

Three `fileMetadata` rules in `docfx.json` then make every fragment invisible as a page, with no change to any fragment file:

```json title="docfx.json (fileMetadata)"
"fileMetadata": {
  "_noindex":        { "**/includes/**": true,  "**/partials/**": true },
  "_enableFeedback": { "**/includes/**": false, "**/partials/**": false },
  "_enableAffix":    { "**/includes/**": false, "**/partials/**": false }
}
```

Search engines and site search skip fragments, and fragments never show a feedback form or sidebar. The same snippets also build the PDF covers: each guide's `cover.md` includes the shared title, version, and release date, so updating `version.md` updates every cover.

**Example:** the success and error messages a user can see when saving permissions lived in one partial that any admin task could include, so a change to those messages was one edit.

### Terms and notices

For short, repeated text, writers type a placeholder. A script in the theme loads a JSON dictionary and swaps each placeholder for its value when the page loads.

```markdown title="Markdown"
This guide explains how to install {{ product }}.

{{ cloudOnly }}

1. Open the console...
```

```json title="sourcedContent/terms.json"
{ "product": "Product Name" }
```

```json title="sourcedContent/messages.json"
{
  "cloudOnly": {
    "message": "This section applies to the cloud edition.",
    "icon": "fa-cloud"
  }
}
```

Terms come out as plain text. Messages come out as a styled notice with an icon, like the green bar in the page diagram. A product rename is one line in `terms.json`, and a new edition is one entry in `messages.json`.

### Banners from front matter

Some content describes the page itself, not a paragraph. I added custom partials that render only when a page asks for them, so pages without the setting are untouched:

```yaml title="Front matter"
---
uid: configure-message-queue.md
title: Configure the message queue
appliesTo:
  cloud: true
  classic: true
statusMessage: This feature is coming soon.
---
```

```handlebars title="_master.tmpl (excerpt)"
{{#if appliesTo}}{{>partials/appliesTo}}{{/if}}
{{#if statusMessage}}{{>partials/statusMessage}}{{/if}}
```

With a cloud edition and a classic edition documented side by side, readers needed to know whether a page applied to them before they read it. The applies-to banner answered that question above the first paragraph.

### Site-level strings

Text that repeats across a whole site, such as the footer's legal links, support URLs, and the link to the contributor guide, lives in `docfx.json` metadata. The theme reads it, so no site hard-codes it.

## Feature switches instead of forks

DocFX turns interface elements off with `_disable*` flags, such as `_disableToc`. Double negatives like `_disableToc: false` are easy to get backward, especially for contributors who aren't developers. I rewrote the relevant partials to read `_enable*` flags instead, and added new settings for every feature I built:

```json title="docfx.json (globalMetadata excerpt)"
"globalMetadata": {
  "_homePath": "/product-name/",
  "_enableBreadcrumb": true,
  "_enableVersionDropdown": true,
  "_enableFeedback": true,
  "_enableRequestFeature": true,
  "_requestFeatureUrl": "https://community.example.com/product/feature-requests",
  "_enableAskQuestion": true,
  "_askQuestionUrl": "https://community.example.com/product/questions",
  "_enableDownloadPdfs": false,
  "_enableContributionLinksFooter": true,
  "_authorInstructions": "https://docs.example.com/contribute",
  "_appFooter": "Copyright © Company · <a href=\"/legal.html\">Legal notice</a>"
}
```

DocFX applies settings at three levels, and the most specific one wins. I designed every feature to work at all three, so a site can turn a feature on everywhere and switch it off for one folder or one page:

<MetadataCascade />

One example is `_enableWide`. Landing pages need the full width of the screen, and articles need room for the *In this article* sidebar. Pages set `_enableWide: true` in front matter, and the master layout switches the article column from three quarters to full width. I documented every setting, default and custom, in a metadata reference for site owners, marking which ones were custom.

## Navigation that respects versions

The platform had several releases live at once, and each built into its own path on one domain, such as `/21-1/` or `/20-3/`. DocFX had no concept of versions. A reader on the 21.1 install page who wanted the 20.3 install page had to go back to the home page and navigate again.

I added a dropdown to the breadcrumb bar that reads a list of versions from one shared JSON file, removes the version segment from the current URL, and builds the same page's URL for each version:

```js title="main.js (simplified)"
const versionPath = /^\/(\d{1,2}-\d|next)/; // matches /21-1, /20-3, /next
const pagePath = window.location.pathname.replace(versionPath, '');

versions.forEach((v) => {
  $('#version').append($('<option />').val(v.key + pagePath).text(v.value));
});
```

Because the version list lives in one shared file instead of in each build, adding a release is a one-line change that reaches every version of the site at once, with no rebuilds. Each site shows or hides the dropdown with `_enableVersionDropdown`.

## Closing the loop with readers

The default template gives writers no way to hear from readers. I added two channels.

<FeedbackLoop />

**Reader feedback.** Every article ends with *Was this article helpful?* A *No* opens a short survey: *It's wrong*, *It's confusing*, *It's missing information*, *It isn't what I expected*, or *It has broken links or typos*, plus an optional suggestion. The form posts to a script endpoint that adds a row to a sheet with the page URL, the answer, the reason, and the suggestion, and each new row sends an alert to the docs team's chat channel. The form went live in mid-2019 and ran on every site the theme reached. Because it's a partial controlled by `_enableFeedback`, it stays off on fragments and on landing pages.

**Usage analytics.** I added page-view tracking to the theme's scripts partial and configured search tracking to read DocFX's search query parameter, so the team could see what readers searched for. Analytics tools don't report pages with zero views, and those were the pages we most needed to find. So I wrote a script that pulls DocFX's `index.json` page list from every site in storage, compares it with the analytics export, merges duplicate entries such as a page and its anchors or search-result URLs, and tags every page by guide and content type. The output fed a dashboard that showed views by guide and flagged pages no one read, so the team knew which pages to merge, cut, or link to better.

## Search that works for technical readers

DocFX's built-in search splits terms on spaces, hyphens, parentheses, and periods. For customers of a data platform, the periods were a problem: searching for a configuration file such as `install.config` searched for `install` and `config` separately and matched every page that mentioned either word. I overrode the default search worker and removed the period from the separator:

```js title="search-worker.js"
// DocFX default
lunr.tokenizer.separator = /[\s\-\.\(\)]+/;
// Customized: keep periods so file names stay whole
lunr.tokenizer.separator = /[\s\-\(\)]+/;
```

Because this file replaced a default file outright, I added it to the list of overrides I checked against each DocFX release. Together with the `_noindex` rules for fragments, cover pages, and raw API spec files, search returned full, readable pages.

## PDFs that look finished

Many customers couldn't reach the website, so PDFs mattered as much as the site. I customized DocFX's PDF template as its own layer in the same theme package:

- **Covers written in Markdown.** Each guide's cover includes shared snippets for the logo, title, version, and release date.
- **A fix for a DocFX bug.** DocFX's PDF table of contents rendered some headings as empty JavaScript links. I removed the broken links in the table of contents template and sized parent headings above their children.
- **Web-only and PDF-only content.** Two CSS classes, one in each template, hide content in the other format. A link to another guide shows on the web, and a plain reference to that guide's title shows in the PDF.
- **A dated footer and matching icons.** wkhtmltopdf settings add an *Updated* date and a consistent font to each page, and the PDF layer loads the same icon fonts as the site, so callouts look the same in print.
- **A guide for one customer.** A customer asked for a user guide without admin tasks. I added a second table of contents and a separate PDF config that built a user-only PDF from the same Markdown, with no copied content.

## Small fixes with outsized value

- **Callouts that match the products.** I changed the labels in `token.json`, swapped Glyphicons for Font Awesome, and matched the colors to the company's design system, so notes and warnings looked like the notifications customers saw in the apps.
- **Headings that don't hide under the header.** A CSS change stopped the fixed navbar from covering a heading when a reader followed an anchor link.
- **Nested sites without copied files.** A configurable styles path let a section nested one level deeper use the same theme. See [Docs-as-code: Standing it up](/experience/docs-as-code#example-one-theme-two-folder-structures).
- **Captions for free.** The lightbox script uses each image's title or alt text as its caption, and only applies to images in the article.

## Keeping the customizations maintainable

Customizations only add value if the team can keep them working after the person who made them moves on. I built that in:

- **One theme package.** Every customization shipped in a single npm package layered on top of DocFX's default template, so a fix reached every site on its next build. See [Docs-as-code: Standing it up](/experience/docs-as-code).
- **A test site.** The theme repo included a test site that listed a local copy of the theme last, so I could preview a change before publishing it to every site.
- **An upgrade check.** I tracked every default file I had overridden and compared it with each new DocFX release, so the site kept upstream fixes.
- **Documentation for every customization.** I wrote an admin guide on the contributor site with an article for each customization: what it does, which files it touches, which settings control it, and, where I considered alternatives, why I rejected them.

## Results

- **A help site that fit its readers.** Customers on any release and either edition could see what applied to them, move between versions without losing their place, and find file names in search.
- **A feedback loop the default generator doesn't offer.** Reader comments and zero-view reports reached the docs team directly, so decisions about what to fix came from evidence.
- **Shared content written once.** Product names, edition notices, shared steps, legal links, and PDF covers each had one source.
- **Every site configurable without code.** More than 20 settings let each site choose its features, and every site stayed on the same theme.
- **Customizations that could still be upgraded.** A small set of overridden files, tracked against each DocFX release and documented for the next maintainer.

## What this project shows

- **I know which customizations are worth making.** Each change solved a problem I could point to, and I left ideas unshipped when they would add upkeep without helping readers.
- **I understand the tool deeply enough to change it safely.** I worked with DocFX's template layering, partials, metadata, search worker, and PDF pipeline, and fixed a bug in its PDF output.
- **I design for other people to configure.** Settings instead of code, clear names instead of double negatives, and a reference for every option.
- **I measure what I build.** The feedback form and zero-view reports showed which pages helped readers and which ones didn't.
- **I engineer for maintenance.** A minimal set of overrides, an upgrade check, a test site, and documentation meant the work outlasted my time on it.
