# Drafting release notes with AI agents when your org has multiple products, versions, and audiences

Using AI to draft quality release notes from git commits or a work-tracking system (like Jira or Azure DevOps) seems like a straightforward task. Can't you just point an agent to a sprint on a board or a Git repo and tell it to transform completed work into notes? Unless you're lucky, the answer is no. Delineations between products or features may not match delineations between boards or teams. Engineers or PMs may not surface relationships between work items by cross referencing or organizing them in perfect epic > feature > task hierarchies. Code changes and commits offer some clues, but the scope of a release can change, so you can't count on the idea that work merged to a release branch today is confirmation it will make it into prod next week. And even if it does, code changes can't surface critical details like the value a change provides to customers or if end users need to be made aware of a change in the first place. What a mess! But it's a solvable one. Here's one way tech writers can get AI agents the info they need to automate production of release notes.

## What the agent needs to know

Here's what an AI agent needs to know to create an accurate release note from tracked work.

For new or changed functionality:

- Which products the new functionality is added to
- Which versions the new functionality applies to
- What was added or changed, and sometimes why
- How the change benefits the user
- Anything else the user needs to know, like if existing functionality was replaced, or if the new functionality needs to be enabled on the user's end

For bugs:

- Which products the bug affects
- Which versions a fixed bug applies to
- What the problem was and/or how the problem affected users
- What was fixed

For known issues:

- Which products the bug affects
- Which versions a known issue applies to
- How the known issue affects the user
- Any workarounds

## How to inform the agent

Teaching the agent how to find which products and versions completed work applies to isn't always straightforward. Flagship features may be certain to ship, but decisions on whether other work will make it into a release change all the time, even up to the last minute. If a tech writer wants a few days before a release to draft notes and route them through approvals, that usually means tracking down ultra-busy PMs and engineers to ask for clarity. Unfortunately for remote tech writers, a ping may go unanswered for several hours - or more if the team member is on the other side of the world. But there's a way to get their attention asynchronously for a few seconds at a time: **custom fields on work items in the work-tracking system that must be filled out before a work item can be transitioned to a certain status**.

### The fields

Text in a work item's default title and description fields help the agent draft the meat of the notes. But data in other fields help the agent figure out what type of work was completed and which products and releases it applied to. For example, work items typically have fields like these by default:

- **Work item type**: An epic or feature represents new or enhanced functionality, a bug represents a fixed or known issue
- **Status**: A status shows if work is in progress, undergoing testing, on pause, or complete, but as a standalone value it doesn't answer questions like which release the work is part of, or for which product
- **Links to related work items**: A feature that tracks to an epic can give the agent added context about new functionality
- **Link to repo commit**: A repo commit can be traced to a release branch but until release day, it's never certain if work merged today will make it to prod next week

But these alone aren't enough. Custom fields like these give the agent additional context it needs to decide what work needs notes and organize them. (It wouldn't make sense to use all these at once. I'm listing several in case some combination works for an organization's unique circumstances.) **Tip**: Consult with the product and engineering teams before adding new fields. Those teams may see value in collecting the information too, and may have suggestions on ways to do it so multiple teams can benefit.

- **User(s) affected**: `End user segment A`, `End user segment C`, etc.
- **Product(s) affected**: `Product X`, `Product Y`, etc.
- **Version(s) affected**: `10.11.12`
- **Versions(s) to fix**: `10.11.10, 10.11.12`
- **Publish as release note**: Boolean

Depending on an organization's setup, it may be possible to combine fields for simplicity, like audience and product (e.g., `Product X - End user segment A`, `Product Y - End user segment B`, etc.). Also, the existence of a value in a field can substitute for a **Publish as release note** toggle if you add logic later, like notes only need to be drafted for a certain product and user segment combination.

It's best if the custom fields are multi-select for consistency, but sometimes that's hard to keep up if only busy admins can add selection values to custom fields. This is especially true with version numbers, which might need to be added frequently. So if it's easier to ask team members to enter versions manually in a text field, the AI agent usually can infer the intent even if the syntax is not consistent (e.g., `v10.11.12` vs. `v 10.11.12` vs. `10.11.10 and 10.11.12`).

### The requirement

Unless your organization is supremely disciplined, a requirement that the custom fields must be filled out before a work item can be transitioned to a certain status helps make sure the info the agent needs is always included. I say *transitioned* because the values in the custom fields most likely aren't all known the moment a work item is created, and PMs or devs don't always return to update field values entered early on when decisions change. (That's why the later the transition you choose falls in the workflow, the better.) I say *certain* because which status you choose depends on an organization's release workflow. To decide, questions you might need to ask include things like:

- When do you want the agent to draft the notes? If a dev release goes out the week before the prod release, do you want the agent to draft notes off the dev release so you have a week to circulate notes for approval?
- If so, how will you account for work removed or added to the release during that week? Will you have the agent compare the list of work items in the dev release against the list of work items in the prod release to find out if notes you drafted early should be removed or new notes added?
- When are work items transitioned to a complete status? Are all work items connected to a dev released marked complete at that time? Or will you find some still marked in progress or undergoing testing?

## The logic

First, connect your agent tool to MCPs for the work tracking system and GitHub. In the stored instructions for your agent, provide examples of logic equations the agent can use to decide which notes need to be drafted. (This example assumes only work items with a certain combination of product and audience field values should become release notes, like if the audience field includes an **N/A** selection to indicate no release note needs to be created to represent that work.)

```txt

## Example output for notes about Product X for User Segment A

### New functionality

- [Work item type = Epic or feature] + [Product affected = Product X] + [Version affected = 10.11.12] + [Audience = User Segment A]

### Bugs

- [Work item type = Bug] + [Product affected = Product X] + [Version affected = 10.11.12] + [Audience = User Segment A]

### Known issues

- [Work item type = Bug] + [Product affected = Product X] + [Version affected = 10.11.12] + [Status = anything but Done] + [Audience = User Segment A]

```
