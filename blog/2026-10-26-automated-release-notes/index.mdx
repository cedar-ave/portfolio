# Drafting release notes with AI agents when your org has multiple products, versions, and audiences

Using AI to draft quality release notes from git commits or a work-tracking system (like Jira or Azure DevOps) seems like a straightforward task. Can't you just point an agent to a sprint on a board or a Git repo and tell it to transform completed work into notes? Unless you're lucky, the answer is no. Delineations between products or features may not match delineations between boards or teams. Engineers or PMs may not surface relationships between work items by cross referencing or organizing them in perfect epic > feature > task hierarchies. Code changes and commits offer some clues, but the scope of a release can change, so you can't count on the fact that work merged to a release branch today confirms it will make it into prod next week. And even if it does, code changes can't surface critical details like the value a change provides to customers or workarounds to known issues. What a mess! But it's a solvable one. Here's one way tech writers can get AI agents the info they need to draft a quality first draft of release notes.

## What the agent needs to know

First, here's what an AI agent needs to know to create an accurate release note from tracked work.

For new or changed functionality:

- Which product(s) the new functionality is added to
- Which version(s) the new functionality applies to
- What was added or changed, and sometimes why
- How the change benefits the user
- Anything else the user needs to know, like whether existing functionality was replaced, or whether the new functionality needs to be enabled on the user's end

For bugs:

- Which product(s) the bug affects
- Which version(s) a fixed bug applies to
- What the problem was
- What was fixed

For known issues:

- Which product(s) the bug affects
- Which versions(s) a known issue applies to
- How the known issue affects the user
- Any workaround(s)

## How to collect the info the agent needs

Much of that information comes only from the engineering or product teams. Tech writers know it can be hard to get time with those busy team members! But there's a way to get their attention asynchronously for a few seconds at a time: custom fields on work items in the work-tracking system that must be filled out before a work item can be transitioned to a completed status.

### The fields

Data in work item fields can give the agent at least some of what it needs to figure out what work is part of which release(s), and for which product(s).

#### Typical default fields

- Work item type (e.g., epic, feature, task, bug)
- ID
- Title
- Description
- Status
- Link to repo commit (sometimes used, sometimes not)

#### Custom fields

Admins of your work-tracking system can also add custom fields. Here are some examples. It wouldn't make sense to use all of these at once, but I'm listing several in case some combination works for your organization's unique circumstances. Tip: Consult with the product and engineering teams before adding new fields. Those teams may see value in collecting the information too, and may have suggestions on ways to do it so multiple teams can benefit.

- User(s) affected (e.g., `End user segment A`, `End user segment C`, etc.)
- Product(s) affected
- Version(s) affected
- Versions(s) to fix
- Publish as release note (Boolean)

Depending on the organization's setup, it may be possible to combine fields for simplicity, like audience and product (e.g., `Product X - End user segment A`, `Product Y - End user segment B`, etc.).

It's best if the custom fields are multi-select for consistency, but sometimes that's hard to keep up if only busy admins can add selection values. This is especially true with versions, which might be added frequently. But if a team member needs to type in a version number manually, the AI agent can usually infer the intent even if the syntax is not consistent (e.g., `v10.11.12` vs. `v 10.11.12` vs. `10.11.12`).

### The logic

In the stored instructions for your agent, provide examples like this:

```txt
### Product X

#### New functionality

[Work item type = Epic or feature] + [Product affected = Product X] + [Version affected = 10.11.12]

#### Bugs

[Work item type = Bug] + [Product affected = Product X] 
```

#### A warning about the status field

I don't use the status field to identify which notes are part of a release because I like to draft the notes before the release, and work items may not be marked as completed until the day of the release.

- If work is tracked across multiple boards, be aware that they may use different statuses - for example, `Complete` vs. `Done` vs. `Closed`.
- If you're drafting notes before the release, a work item representing work that will be included as part of a release may still have a status of `In progress` or `Open` or `In Testing`.
