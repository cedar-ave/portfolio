# How I use AI and classifications to keep track of great techcomm industry knowledge so I can find answers when I need them

Sometimes I come across a great article, podcast, post, or talk that describes a solution to a challenge I'm not facing now, but probably will in the future. My favorites are first-person accounts of a challenge a docs engineer faced, the research and reasoning behind their solution design, and the tools and methods they used to execute. Revisiting a bookmark like that has saved me more than one time! But sifting through what I've saved is always a chore.

Here's how I built an AI-powered knowledge base for my best sources that answers agent questions like, _What have startups done to implement documentation drift prevention workflows?_ or _What software companies have open-sourced their AI agent skills for automating release notes?_ using a faceted metadata model built on controlled vocabularies and authority records stored in the YAML frontmatter of Markdown files. Yes -- I could just ask an LLM to answer these questions, but the response probably isn't going to draw on that awesome 15-minute block in a podcast, that detailed comment on that LinkedIn post, or that insightful blog post hosted on a personal portfolio site.

And yes, I went way overboard on this!

## The plan

First, I gave Claude a couple dozen examples of questions I might ask my knowledge base now or in the future, like:

- How do I keep documentation from drifting from product truth?
- How do I best use evals in my AI skills that draft content?
- What are examples of how companies automated release notes?
- How can analyze support tickets so they inform help center content?
- I'm the first tech writer at a startup. How should I set up an AI-powered docs ecosystem?
- What is the latest thinking on docs metrics?

Claude helped me create a plan to optimize my sources so that when I asked an agent a question, the agent could easily scan them, read their contents, and return an answer. The plan settled on:

- One Markdown file for each source
- YAML frontmatter block with schema fields at the top of each Markdown file
- Vocabulary with synonyms and definitions to support a classification scheme
- Source classifications like what stage of the docs lifecycle it fits in (like strategy, drafting, validation, etc.), a doc type (like API docs vs. release notes), organizational context (like a startup vs. enterprise), and more 
- Retrieval evals that test processed sources against my questions

## The data model

Claude scanned schemas it recommended ([Google Open Knowledge Format](https://github.com/GoogleCloudPlatform/open-knowledge-format), [Dublin Core](https://www.dublincore.org), [manni](https://hawkeyexl.github.io/manni/meta/reference/schema-resolution/#the-default-set)) and created a custom one based on my use case. Here's an example of how an article about [docs metrics](https://sdeaton.com/blog/docs-metrics-stories) is classified:

```yaml
id: web:sdeaton.com/blog/docs-metrics-stories
type: article
title: Docs metrics and the stories we tell ourselves
description: Sarah Deaton on why docs metrics are fuzzy, incomplete and easy to bend into whatever story we already believe, and her four-step plan to measure anyway and get "less wrong" over time.
resource: https://sdeaton.com/blog/docs-metrics-stories/
authors:
  - sarah-deaton
published: 2025-09-23
captured-on: 2026-10-29
concepts:
  - Docs metrics
  - Data-informed documentation
  - Page feedback widgets
  - Content quality
  - AI traffic to docs
genre:
  - opinion
knowledge-types:
  - best-practice
lifecycle-stages:
  - analytics
tools:
  - mintlify
  - looker-studio
  - microsoft-excel
  - grafana
first-hand: true
part-of: web:sdeaton.com
```

My favorite part is `first-hand: true`. That tells the agent to give me real-life examples when I ask for them!

The other part I love is that the YAML frontmatter also includes sample questions. The AI agent uses these to help guide which sources it retrieves.

```yaml
sample-questions:
  - Why does metadata matter for RAG-based AI answers over documentation?
  - How do I define a controlled vocabulary and frontmatter schema for a docs-as-code site?
  - Can Vale enforce frontmatter values, and what do I need for missing-field checks?
  - How can I retrofit metadata onto an existing docs set without a big one-off project?
  - Should an LLM be allowed to tag my docs, and how do I keep it within my vocabulary?
```

### Vocabulary

Each term got a definition and synonyms. For example, for organizational context:

**Enterprise:**
- large company; big tech; large organization
- Use for large organizations with established process and scale.

**Open source:**
- OSS; open-source project; community-maintained project
- Use when the docs belong to an open-source project.

**Scaleup:**
- scale-up; growth stage; mid-size company
- Use for growth-stage companies building process and teams.

**Solo writer:**
- lone writer; team of one; solo technical writer; first tech writer
- Use when the item addresses one writer working alone, including the first writer hired.

**Startup:**
- early-stage startup; small company; seed-stage
- Use when the context is an early-stage company with few people and little process.

## The classification

Claude then processed each article and applied the schema. 

At the same time, it created one Markdown file per event (like a certain conference), associated people (like the author or people interviewed for a podcast), series (like a collection of articles released as a bundle), and tools (like an platform reviewed in a blog post or an open-source linting tool used in a CI/CD pipeline). ## Segments

A source may cover more than one topic, especially a recording of a talk or podcast. Claude catalogs each topic covered as a separate segment, like these few minutes on chat log analysis:

## The evals

manni meta validate
Using manni.config.yaml (.)

Claude created an eval around _golden questions_ that tested queries around each of my initial questions to see if correct sources were returned. Results were divided between _must_ and _nice_. For example, here are the sources found when an agent asked, `How do I keep documentation from drifting from product truth?`:

## The reference material

The sources aren't just for agents to read.


```md
## Summary

Tom Johnson (I'd Rather Be Writing, October 25, 2026) describes a two-stage strategy for improving docs from AI chat-session logs: turn chat failures into doc tickets, then fix them with a `fix-doc-bugs` skill and check each fix with an eval built from the original failing prompt. The real bottleneck is review, not generation.

## Key takeaways

- **Chat logs are a new, rich source of user feedback** (sanitized for PII). Few tech writers have had this before.
- **Tap "input streams":** support and other teams already analyze logs but rarely connect friction to docs. Meet with them, funnel their doc gaps into your intake queue, and report back on fixes, because people stop filing when tickets sit.
- **Own log analysis too:** a skill that turns messy logs into specific doc recommendations produced tickets that were easy to work and proved the logs → tickets → fixes pipeline.
- **Triage tickets from non-writers** before fixing. Watch for bundled unrelated issues, edits to auto-generated files a build would overwrite, content you don't own (legal/policy), designs that aren't agent-readable, changes a pending release would overwrite, and single instances of a corpus-wide pattern.
- **Build a fix skill that applies writer judgment:** first ask whether the ticket should be fixed at all, then review the whole product doc set so the update fits instead of bolting on a note. It checks in-flight CLs/PRs for conflicts, finds SME reviewers from file history and owners, links code elements to reference docs, uses adversarial subagents to fact-check, edits reference docs in source (not generated HTML), handles GitHub-hosted samples, stages CLs with preview links, formats Markdown to pass linters, and runs a self-reflection loop to improve itself.
- **Tag every generated CL with the skill name** as telemetry to see who uses it.
- **Review is the constraint:** 100 tickets overnight become 100 CLs by morning, but SME review and juggling ~10 active CLs don't scale. SMEs approved roughly 90% (ballpark) with little back-and-forth; the misses were in product areas he didn't know well, so domain-expert writers steer the skill better.
- **Measure fixes with evals, not failure rates.** Log failure rates are slow and noisy. Turn the original failing chat prompt into an eval and rerun it against the updated docs. Rule of thumb: chat-failure fixes get an eval; trivial fixes like broken links don't.

## Tools mentioned

- **`fix-doc-bugs` skill** (custom, internal): turns doc tickets into staged CLs with the behaviors above.
- **Log-analysis skill** (custom, internal): turns chat logs into specific doc recommendations. He's built 30+ internal authoring skills in the past year (release notes, policy updates and more).
- **GitHub**: where code samples and assets live; the skill handles them there.
- **Style linters**: the skill formats Markdown to pass them (no specific linter named).
- Unnamed AI tools he's evaluating to monitor CL status and ping silent SMEs.
```
