# The OpenAPI spec and reference page

The reference page at `/api-reference` is rendered by [Scalar](https://scalar.com/products/api-references/integrations/docusaurus) from one OpenAPI 3.1 file, `static/openapi/norway-data.yaml`. Everything on the page comes from that file, including the conceptual docs.

<QuickReference>

- `@scalar/docusaurus` adds the `/api-reference` route. It loads Scalar's script from a CDN, pinned to a specific version.
- The plugin's own navbar link is turned off (`showNavLink: false`) and replaced with a hand-added link, so the link goes where the rest of the navbar puts it.
- The spec's `info.description` holds the conceptual docs: quick start, data model, request rules, pagination, caching, rate limits, errors, versioning, changelog, and notes on the data. Each `##` heading becomes its own section.
- Every example in the spec is the real response to a known request. The [contract test](contract-test) fails if one drifts.
- Run `npm run lint:api` to lint the spec with Redocly.

</QuickReference>

## The plugin

```js title="docusaurus.config.js"
plugins: [
  // ...
  [
    '@scalar/docusaurus',
    {
      route: '/api-reference',
      showNavLink: false,
      // Pinned so a Scalar release can't change the page unannounced.
      cdn: 'https://cdn.jsdelivr.net/npm/@scalar/api-reference@1.73.1',
      configuration: {
        url: '/openapi/norway-data.yaml',
      },
    },
  ],
],
```

- **`route`** is the page's URL.
- **`showNavLink: false`** stops the plugin from adding its own navbar link. The plugin always appends its link to the end of the left side of the navbar, so the link is added by hand in `themeConfig.navbar.items` instead:

  ```js title="docusaurus.config.js"
  {
    to: '/api-reference',
    label: 'Norway Data API',
    position: 'left',
  },
  ```

- **`cdn`** pins Scalar's script version. The plugin loads the latest version by default, which could change the page with no change in this repo. To upgrade, change the version number and check the page.
- **`configuration.url`** points at the spec. Files in `static/` are served from the site root, so `static/openapi/norway-data.yaml` is at `/openapi/norway-data.yaml`.

:::note

The plugin adds Scalar's `<script>` tag to every page on the site, not only `/api-reference`. That's how the plugin is built. If page weight on other pages ever matters, replace the plugin with a custom page that loads Scalar only on its own route.

:::

The plugin hides Scalar's dark mode toggle, and the page follows the site's light or dark mode.

## Spec layout

| Part | Contents |
| --- | --- |
| `info.description` | The conceptual docs (see [The introduction](#the-introduction)) |
| `info.contact` | Links to the repo's GitHub Issues, so readers know where to report a problem |
| `info.license` | MIT, the same as the repo |
| `servers` | The production base URL, `https://www.marlasowards.com/api/norway-data/v1`. Scalar's generated code samples use it, which is why they work as-is. |
| `security: []` | States that there's no authentication. Without it, Redocly's `security-defined` rule fails. |
| `tags` | One per resource: Index, Facts, Categories, Places |
| `paths` | One `get` per endpoint |
| `components` | Shared parameters, headers, schemas, and responses |

### Conventions in the spec

- **Response schemas use `additionalProperties: false`.** If the function starts returning a field the spec doesn't list, the contract test fails.
- **Values that can gain new options are open strings.** `CategoryId` and a place's `type` are `type: string` with the current values in the description, not an `enum`. Code generators turn an `enum` into a closed type that would reject a value added later, which would contradict the docs' promise that new values can appear within `v1`. The `category` query parameter is still an `enum`, since it's input the API validates.
- **Schemas use `examples` (an array), not `example`.** `example` inside a schema is deprecated in OpenAPI 3.1. Parameter and media type objects still use `example`, which isn't deprecated there.
- **Descriptions link to the introduction instead of repeating it.** For example, the `Limit` parameter says `See [Pagination](#description/pagination).` rather than restating the pagination rules. Each rule has one home, so they can't drift apart.
- **Shared responses are components.** `BadRequest`, `NotFound`, `NotModified`, `TooManyRequests`, and `InternalError` are defined once and referenced by each operation.

## The introduction

`info.description` is Markdown that Scalar shows above the endpoints. The text before the first heading is a short overview. Each `##` heading after it is its own section:

| Section | Covers |
| --- | --- |
| Quick start | A first request and its response |
| Authentication | None needed |
| Data model | Facts, categories, places, how they relate, and how IDs work |
| Request rules | Base URL, methods, strict parameters, unknown paths, CORS |
| Response format | JSON conventions and the collection vs. single-resource rule |
| Pagination | `limit`, `offset`, and page links |
| Caching | `ETag`, `304`, and which responses are never cached |
| Rate limits | The limit and what a `429` looks like |
| Errors | The problem details format and a table of every error `type` |
| Versioning | What can change within `v1` |
| Changelog | One row per release |
| About the data | Sources, language, license, and where to report issues |

Scalar gives each heading an anchor of `#description/` plus the heading text in lowercase, with spaces replaced by hyphens. That's how descriptions elsewhere in the spec link to sections, such as `#description/caching`. **If you rename a heading, search the spec for links to its old anchor.**

Error `type` values deliberately don't use these anchors. An earlier version did (`https://www.marlasowards.com/api-reference#description/not-found`), which meant renaming a heading would change a value clients branch on. See [Design decisions](design-decisions).

## Examples are real responses

Every example in the spec is the exact response to a specific request, so the docs can't show something the API wouldn't send. There are two kinds:

**Examples in the introduction.** A fenced `json` block that comes right after a fenced `bash` block containing a `curl` command is that command's response:

````markdown
```bash
curl https://www.marlasowards.com/api/norway-data/v1/facts/10
```

```json
{
  "id": 10,
  ...
}
```
````

**Examples on endpoints and shared responses.** A media type with an `example` also has an `x-example-request` with the path that produces it:

```yaml title="norway-data.yaml"
content:
  application/json:
    schema:
      $ref: '#/components/schemas/Place'
    x-example-request: /places/sognefjord
    example:
      id: sognefjord
      name: Sognefjord
      ...
```

Scalar ignores `x-` extensions unless it's configured to show them, so `x-example-request` doesn't appear on the page.

The [contract test](contract-test) makes each request and compares the response to the example. The only examples without a request are `/random-fact` (its response is random) and `InternalError` (the API can't be made to fail on purpose). Those are still checked against their schemas.

Examples that include a `requestId` use the placeholder `01JEXAMPLE0REQUEST0ID00000`. The contract test passes that same value to the function, so error examples match exactly.

## Linting

```bash
npm run lint:api
```

This runs a pinned version of Redocly's CLI with its built-in `recommended` rules. The spec currently passes with no errors or warnings. The `api` job in GitHub Actions runs the same command.
